# AI Provider Settings UX Design

Date: 2026-06-22
Status: Milestone implementation contract

## Goal

Make the Control Center AI provider settings safe and testable. A user must be able to edit `baseUrl`, `model`, and API key, clearly understand whether edits are only local drafts or already active, save them intentionally, and run a connection test that returns actionable feedback without exposing secrets.

This closes the current gap where fields are editable but the UI does not clearly distinguish "typed", "saved", and "tested" states.

## P0 Scope

- API keys stay in the main-process `SecretService`.
- Renderer receives only `hasApiKey` and non-secret status metadata.
- Logs never include API key values, authorization headers, full prompts, or provider response bodies.
- Ordinary plugins still cannot read raw provider credentials.

## P1 Scope

- Add a structured `AiConnectionTestResult` contract for provider tests.
- Show active saved config separately from unsaved draft config.
- Detect unsaved edits for `enabled`, `provider`, `baseUrl`, `model`, `systemPrompt`, and memory toggle.
- Validate `baseUrl` and `model` before saving or testing.
- Provide clear actions:
  - save provider config;
  - save API key;
  - save config and test;
  - test currently saved config.
- Show connection test result with provider, base URL, model, API key presence, elapsed time, status, and safe error code/message.
- Cover the main-process privacy boundary and UI state logic with tests where practical.

## Non-Goals

- Provider presets.
- `/models` discovery.
- Test history list.
- Streaming chat replies.
- Persona editor UX.
- Desktop floating-window chat.
- Full AI pane redesign.

## User Flow

1. User edits provider settings in Control Center.
2. UI marks the form as "unsaved draft" and keeps showing the active saved provider summary.
3. User may save only config, save only key, save config and immediately test, or test the already saved config.
4. Connection test calls the main process only.
5. Main process reads saved settings and secret, sends a minimal "Reply with ok." request, and returns a structured safe result.
6. UI shows success or actionable failure without exposing sensitive content.

## Connection Test Contract

```ts
interface AiConnectionTestResult {
  ok: boolean
  provider: string
  baseUrl: string
  model: string
  hasApiKey: boolean
  elapsedMs: number
  reply?: string
  code?: string
  message?: string
}
```

`reply` is only present on success. On failure, `code` and `message` must be safe display values generated by OpenPet, not raw provider error bodies.

Recommended error codes:

- `missing_api_key`
- `unsupported_provider`
- `timeout`
- `unauthorized`
- `forbidden`
- `rate_limited`
- `provider_unavailable`
- `provider_error`
- `network_error`
- `unknown_error`

## Security Notes

- `saveAiApiKey()` accepts the raw draft key through IPC and immediately stores it in `SecretService`; it must not persist in renderer state after success.
- `testAiConnection()` must not accept a raw key or draft key payload.
- The UI cannot test unsaved API key text directly. "Save and test" first saves config and key, then tests active saved settings.
- Provider logs include only safe metadata: provider, base URL, model, API key presence, elapsed time, and safe error code.

## Acceptance

- A user can configure `http://127.0.0.1:8317/v1`, model `gpt-5.5`, save the API key, then press "保存并测试" and see a concrete pass/fail result.
- Pressing "测试当前已保存配置" never uses unsaved drafts.
- Failed tests distinguish missing key, unsupported provider, timeout, auth failure, rate limit, provider failure, and network failure.
- Tests prove provider failures do not leak API keys or full prompts through return values or app logs.
